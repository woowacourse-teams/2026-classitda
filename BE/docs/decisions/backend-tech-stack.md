## Spring Boot

- 후보: Spring Boot 3, 4
- 선택: Spring Boot 4.1.0

### 🤔 선택 근거

#### 변경 가능한 API에 대응하기 위해서예요

이번 프로젝트는 초기부터 기능 명세가 완전히 확정된 상태에서 개발하는 프로젝트가 아니에요.

먼저 가설을 세우고, 사용자 인터뷰와 검증을 통해 가설을 확인해나가면서 서비스를 발전시킬 계획이에요.

이 과정에서 기존 기능이 폐기되거나, 기존 기능의 요구사항이 변경되거나, 새로운 기능이 추가될 수 있어요. 이러한 변경은 API의 요청과 응답 형식에도 영향을 줄 수 있어요.

기존 API를 사용하는 클라이언트와의 호환성을 고려하지 않으면, API를 변경할 때마다 클라이언트도 함께 수정해야 하는 문제가 발생해요.

이러한 문제에 대응하기 위해 API Versioning을 활용하려고 해요.

Spring Boot 4에서 사용하는 Spring Framework 7은 Spring MVC의 API Versioning 기능을 제공해요. 이 기능을 활용하면 API 경로에 버전을 직접 포함하지 않고, 요청 헤더 등을 통해 API 버전을 구분할 수 있어요.

이를 통해 기존 API를 유지하면서 새로운 API 버전을 추가할 수 있고, 가설 검증 과정에서 발생하는 기능 변경이 기존 클라이언트에 미치는 영향을 줄일 수 있어요.

```text
GET /api/members/1
X-API-Version: 1.0.0

GET /api/members/1
X-API-Version: 2.0.0
```

#### API 변경을 일관된 방식으로 테스트하기 위해서예요

API 변경이 잦을 것으로 예상되기 때문에, 변경된 API가 각 버전에서 의도한 대로 동작하는지 지속적으로 검증할 수 있는 테스트 환경이 필요해요.

Spring Framework 7에서 제공하는 `RestTestClient`는 서버를 직접 실행하지 않는 MockMvc 기반 테스트와 실제 서버를 대상으로 하는 통합 테스트를 동일한 방식으로 작성할 수 있도록 지원해요.

따라서 API Versioning에 따른 버전별 요청과 응답을 일관된 방식으로 검증할 수 있어요. 또한 테스트 방식에 따라 MockMvc와 RestAssured를 별도로 나누어 사용하는 복잡성도 줄일 수 있어요.

#### Spring Boot 생태계의 지원 방향을 고려했어요

Spring Boot 3.5.x 계열의 마지막 OSS 릴리스인 3.5.16에서는 이후에도 OSS 지원을 계속 받기 위해 Spring Boot 4.0.x 또는 4.1.x로 업그레이드할 것을 안내하고 있어요.

따라서 지속적인 유지보수와 최신 Spring 생태계의 지원을 고려해 Spring Boot 4.1.0을 선택했어요.

## 영속성 기술

- 후보: JPA, JDBC, MyBatis
- 선택: Spring Data JPA

### 🤔 선택 근거

#### 반복적인 SQL 작성 부담을 줄이기 위해서예요

JDBC와 MyBatis는 개발자가 SQL을 직접 작성하고, 조회 결과를 객체로 변환하는 작업도 직접 처리해야 해요.

반면 Spring Data JPA는 엔티티와 객체 간 매핑을 기반으로 기본적인 SQL을 자동 생성할 수 있어요. 또한 메서드 이름을 활용한 쿼리 생성이나 JPQL을 사용할 수도 있어요.

이를 통해 반복적인 SQL 작성과 결과 매핑에 드는 부담을 줄일 수 있다고 판단했어요.

### 현재 도메인에 적합하다고 판단했어요

이번 프로젝트의 주요 기능은 수업 예약과 1:1 DM이에요. 복잡한 통계 쿼리나 대규모 데이터 분석이 핵심인 서비스는 아니에요.

JPA는 복잡한 통계 쿼리나 세밀한 SQL 튜닝에는 불리할 수 있지만, 현재 서비스의 일반적인 CRUD와 도메인 객체 중심의 데이터 접근에는 적합하다고 판단했어요.

JPA로 처리하기 어려운 복잡한 조회나 성능 최적화가 필요한 경우에는 JdbcTemplate을 함께 사용해 필요한 쿼리만 직접 작성할 예정이에요.

## 데이터베이스

- 후보: MySQL, PostgreSQL
- 선택: MySQL 8.4 LTS

### 🤔 선택 근거

#### 현재 도메인에 필요한 기능을 기준으로 판단했어요

PostgreSQL은 벡터 검색, 지리 정보 처리, 복잡한 분석 쿼리, JSONB 중심의 데이터 구조 등에서 강점을 가지고 있어요.

하지만 현재 프로젝트의 주요 기능인 수업 예약과 1:1 DM에서는 이러한 PostgreSQL의 강점을 반드시 활용해야 하는 요구사항이 없어요.

따라서 PostgreSQL이 더 많은 기능을 제공한다는 이유만으로 선택하기보다는, 현재 도메인에 필요한 기능을 안정적으로 제공하는지를 기준으로 판단했어요.

#### 팀이 문제를 진단할 수 있는 기술을 선택했어요

데이터베이스 장애나 성능 문제가 발생했을 때 원인을 빠르게 파악하고 대응할 수 있어야 해요.

팀은 MySQL의 InnoDB 버퍼 풀, B+Tree 인덱스, 클러스터드 인덱스, 락 모델, 옵티마이저 등에 대한 지식을 보유하고 있어요.

따라서 MySQL을 사용하면 실행 계획을 분석하고 인덱스나 쿼리 문제를 진단하는 과정에서 팀의 기존 지식을 활용할 수 있어요.

반면 PostgreSQL을 선택하면 새로운 내부 동작과 운영 방식을 추가로 학습해야 하기 때문에, 현재 프로젝트에서는 유지보수 부담이 커질 수 있다고 판단했어요.

#### 안정적인 버전을 선택했어요

MySQL 8.4는 장기 지원을 제공하는 LTS 버전이고, MySQL 9.x는 새로운 기능을 빠르게 제공하는 Innovation 버전이에요.

이번 프로젝트에서는 새로운 기능을 빠르게 도입하는 것보다 안정적인 운영과 예측 가능한 변경을 우선하기 때문에 MySQL 8.4 LTS를 선택했어요.

### 😥 한계점

PostgreSQL은 부분 인덱스를 지원해서 `WHERE status <> 'CANCELED'` 같은 조건을 유니크 인덱스에 직접 걸 수 있지만, MySQL에는 이 기능이 없어요.

그래서 취소된 행이 유니크 제약을 계속 점유하는 문제를 생성 컬럼(`GENERATED ALWAYS AS`)으로 우회하고 있어요. 취소, 만료 상태를 가진 테이블이 늘어날수록 같은 우회를 반복해야 해요.

다만 현재 우회가 필요한 유니크 제약은 4개뿐이라, PostgreSQL을 새로 학습하고 운영하는 비용보다 우회 비용이 작다고 판단했어요.

## Docker

### 🤔 선택 근거

- 로컬 데이터베이스와 향후 추가될 Redis, Nginx 등의 기술을 컨테이너로 실행해 개발자마다 다른 설치 버전이나 설정으로 인해 발생할 수 있는 환경 차이를 줄이고, 간편하게 실행할 수 있도록 하기 위해 Docker를 사용하기로 했어요.
- 또한 다른 파트인 안드로이드에서도 배포 전에 백엔드 서버를 쉽게 실행하고 연동 테스트를 할 수 있도록, Docker Compose를 사용해 백엔드 서버와 데이터베이스 등 여러 컨테이너를 하나의 구성으로 묶어 한 번에 실행할 수 있도록 했어요.
