# ADR-0002. 스튜디오 경계 무결성을 애플리케이션에서 검증해요

- 상태: 채택 (2026-08-06)
- 후보: 복합 외래 키로 DB에서 강제, 애플리케이션 서비스 계층에서 검증
- 선택: 애플리케이션 검증
- 관련: [ADR-0003](0003-schema-source-of-truth.md), [ADR-0006](0006-layer-contract.md)

---

## 🤔 선택 근거

### 외래 키는 "존재하는 id인가"만 보장해요

`reservation.member_pass_id`에 외래 키가 걸려 있어도, DB는 그 수강권이 **예약하는 회원의 것인지** 확인하지 않아요. 존재하기만 하면 통과해요. 남의 수강권 id를 넣은 요청은 FK를 그대로 통과해서 저장돼요.

우리 도메인은 거의 모든 테이블이 스튜디오에 속하고, "같은 스튜디오 안의 것끼리만 연결된다"가 핵심 불변식이에요. 그런데 이건 단일 컬럼 FK로는 표현되지 않는 종류의 제약이에요.

### 복합 FK로 막으려면 스키마 전체가 무거워져요

DB로 강제하려면 참조되는 쪽에 `(id, studio_id)` 유니크 키를 추가하고, 참조하는 쪽이 `studio_id`를 비정규화로 들고 있어야 해요. 그다음 `(대상_id, studio_id) → (id, studio_id)` 복합 FK를 걸어요.

경계가 걸린 테이블이 7곳이라 다음을 감수해야 해요.

- 참조하는 테이블마다 `studio_id` 중복 컬럼과 그 값을 맞춰 넣는 책임이 생겨요.
- 참조되는 테이블마다 실질적으로 쓰이지 않는 보조 유니크 인덱스가 하나씩 늘어요.
- JPA에서는 같은 컬럼이 연관관계 매핑과 중복 컬럼 양쪽에 물려서, 한쪽을 `insertable = false, updatable = false`로 두고 다뤄야 해요. 매핑이 복잡해지는 만큼 실수 지점도 늘어요.

가설을 검증하며 스키마가 자주 바뀌는 단계라, 이 비용이 지금 얻는 안전보다 크다고 판단했어요.

### 검증 실패를 사용자에게 설명해야 해요

FK 위반은 DB에서 예외로 올라와요. 이걸 "본인 수강권이 아니에요" 같은 메시지로 바꾸려면 결국 애플리케이션이 예외를 해석해야 해요. 어차피 애플리케이션이 관여할 거라면, 저장을 시도하기 전에 확인하고 도메인 예외를 던지는 편이 흐름이 단순해요.

## 규칙

### 저장 전에 확인해야 하는 불변식

아래는 **DB가 잡아주지 않아요.** 서비스가 저장 전에 확인해야 해요.

| 불변식 | 어기면 |
| --- | --- |
| `class_session`의 studio = template·room·instructor의 studio | 다른 스튜디오 룸에 수업이 열려요 |
| `class_template`의 studio = instructor membership의 studio | 남의 스튜디오 강사가 배정돼요 |
| `reservation`의 membership studio = 그 session의 studio | 다른 스튜디오 회원이 예약해요 |
| `reservation`의 member_pass 소유 membership = reservation의 membership | **남의 수강권으로 예약돼요** |
| `member_pass`의 membership studio = pass의 studio | A 스튜디오 수강권이 B 스튜디오 회원에게 발급돼요 |
| `notice`의 author membership studio = notice의 studio | 외부인이 공지를 작성해요 |
| `studio_membership`의 studio_role studio = membership의 studio | 다른 스튜디오 역할이 부여돼요 |

### 시간 겹침도 애플리케이션 책임이에요

`class_session`의 유니크 제약(`uk_session_room_active`, `uk_session_instructor_active`)은 **시작 시각이 정확히 같을 때만** 막아요. 09:00~10:00 수업이 있는 룸에 09:30~10:30 수업을 넣는 건 DB를 그대로 통과해요.

같은 룸·같은 강사에 구간이 겹치는 세션은 애플리케이션이 걸러야 해요.

### 검증은 한 곳에 모아요

이 검증들을 여러 서비스에 흩어 놓지 않아요. 흩어지면 언젠가 한 곳이 빠지고, **그 경로로만** 잘못된 데이터가 들어와요. 그런 데이터는 나중에 원인을 찾기가 어려워요.

### 설계·리뷰 단계에서 강제해요

- 설계 문서에 **검증 위치를 명시**해요. "어디서 검증하는지"가 안 적힌 설계는 구현에서 빠져요.
- 리뷰에서 경계 검증·시간 겹침 검사 누락을 확인 항목으로 둬요. DB가 안 막으니 리뷰가 마지막 방어선이에요.

---

## 감수하는 점

- **서비스가 검증을 빠뜨리면 잘못된 데이터가 그대로 저장돼요.** DB에 안전망이 없어요. 이게 이 결정의 가장 큰 비용이고, 위의 "한 곳에 모은다"와 리뷰 항목화가 그 대응이에요.
- **동시 요청에는 검증만으로 부족할 수 있어요.** 정원 초과나 겹침처럼 읽고 나서 쓰는 사이에 상태가 바뀔 수 있는 검사는, 필요해지는 시점에 잠금이나 유니크 제약을 추가로 검토해요.
- 데이터가 늘어난 뒤 경계 위반이 실제로 발생하면, 그때 복합 FK 도입을 다시 판단해요. 그때는 새 ADR로 남겨요.
