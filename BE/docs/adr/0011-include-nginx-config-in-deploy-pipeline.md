# ADR-0011: nginx 운영 방식을 배포 파이프라인에 통합한다

## Status

Proposed

## Context

nginx는 애플리케이션과 같은 `compose.prod.yml`에 컨테이너로 정의되어 EC2에서 동작한다. 그런데 관리 방식이 어중간한 상태로 남아 있다.

- **`compose.prod.yml`은 저장소에 있고 nginx 서비스를 선언한다.** `./nginx/api.conf`를 마운트한다.
- **`nginx/api.conf`는 저장소에 없다.** 서버의 `/opt/classitda/nginx/api.conf`에만 존재한다. 저장소를 클론해 `compose.prod.yml`로 띄우면 마운트 대상이 없어 실패한다.
- 커밋을 보류한 이유는 이 파일에 TLS 인증서 **경로**가 드러나는 것이 꺼려졌기 때문이다. 경로 자체는 자격증명이 아니고 서버에 접근하면 `nginx -T`로 즉시 확인되지만, 팀 방침으로 정해지지 않았다.
- **배포 워크플로는 `docker compose up -d --pull always app`으로 애플리케이션 컨테이너만 교체한다.** nginx는 배포 대상이 아니며, `restart: unless-stopped`로 계속 떠 있다.
- 따라서 nginx 설정을 바꾸려면 사람이 `scp`로 옮기고 리로드해야 한다. `api.conf`는 바인드 마운트라 파일 내용이 바뀌어도 compose가 감지하지 못하므로, 전송만으로는 부족하고 명시적인 리로드가 필요하다.
- 파이프라인에 포함하는 구성을 한 차례 구현했다가, nginx 운영 방식을 확정하지 못해 되돌린 이력이 있다.

## Decision

두 가지를 함께 정할 것을 제안한다.

1. **`nginx/api.conf`를 저장소에 포함한다.** TLS 인증서의 내용이 아니라 경로만 드러나므로 자격증명 노출이 아니고, 설정 변경이 리뷰를 거치게 된다. 경로 노출이 계속 걸린다면 `ssl_*` 지시어만 서버 전용 `include` 파일로 분리하는 절충안을 택한다.
2. **배포가 `compose.prod.yml`과 `nginx/api.conf`를 서버로 전송하고, 배포 성공 후 `nginx -t`로 검증한 뒤 `nginx -s reload`를 수행한다.** 배포 명령은 `app`만이 아니라 스택 전체를 대상으로 한다. `docker compose up -d`는 선언적이라 설정이 바뀌지 않은 서비스는 재생성하지 않으므로 평소 동작은 지금과 같고, nginx가 사라진 경우에만 복구된다.

## Alternatives

- **현행 유지** — 변경이 드물어 감당 가능하지만, 저장소와 서버가 어긋나도 알아챌 방법이 없고 nginx가 사라지면 배포로 복구되지 않는다. 무엇보다 **`compose.prod.yml`이 저장소에 없는 파일을 참조하는 모순이 남는다.**
- **`compose.prod.yml`에서도 nginx 서비스를 제거** — 저장소의 모순은 사라지지만, 서버 구성이 어디에도 기록되지 않는 상태로 되돌아간다.
- **nginx 전용 워크플로 분리** — 관심사가 분리되지만 워크플로가 하나 늘고 애플리케이션 배포와 순서를 맞추기 어렵다.
- **Ansible 등 구성 관리 도구 도입** — 서버 설정 전반을 코드화할 수 있으나, 관리 대상이 한 대뿐인 지금 도구를 하나 더 들이는 비용이 크다.

## Consequences

- (+) **저장소와 실제 서버 구성이 일치한다.** 지금은 `compose.prod.yml`이 존재하지 않는 파일을 참조하고 있다.
- (+) nginx 설정 변경이 다른 코드 변경과 같은 리뷰·이력·배포 경로를 따른다.
- (+) nginx가 어떤 이유로 사라져도 다음 배포가 복구한다.
- (+) 새 서버를 세울 때 손으로 옮길 파일이 줄어든다.
- (-) **잘못된 설정을 머지하면 서비스 전체가 영향을 받는다.** 애플리케이션 배포는 헬스체크 실패 시 롤백되지만, nginx 설정 롤백은 별도로 마련해야 한다. `nginx -t`는 문법만 검증하므로 `ssl_verify_client` 삭제처럼 문법이 맞는 위험한 변경은 잡지 못한다.
- (-) 배포 job이 저장소를 checkout해야 하므로 스텝이 늘어난다.
- (=) `nginx -s reload`는 처리 중인 요청을 끊지 않으므로 다운타임은 생기지 않는다.
- (=) TLS 인증서(`/etc/ssl/cloudflare/*`)는 시크릿이므로 전송 대상에서 제외한다. 서버에만 두고 만료까지 손대지 않는다.
- 재검토: 채택하면 `Accepted`로 바꾸고, 채택하지 않기로 하면 `compose.prod.yml`에서 nginx 서비스를 제거해 저장소의 모순을 없앤 뒤 현행 유지를 결정으로 기록한다.

## Compliance

채택 시 다음을 확인한다.

- 저장소를 클론한 상태에서 `compose.prod.yml`이 참조하는 파일이 모두 존재하는지
- `api.conf`를 수정한 커밋이 머지된 뒤 서버의 `/opt/classitda/nginx/api.conf`가 같은 내용인지
- 배포 로그에 `nginx -t` 통과 기록이 남는지
