# ADR-0007. 계층마다 격리 수준을 다르게 하고, 검증 수단을 임의로 바꾸지 않아요

- 상태: 채택 (2026-08-06)
- 후보: 통합 테스트 위주로 한 벌, 계층별로 격리 수준을 나누기
- 선택: 계층별 격리 + Repository만 실제 MySQL
- 관련: [ADR-0003](0003-schema-source-of-truth.md), [ADR-0006](0006-layer-contract.md)

---

## 🤔 선택 근거

### 계층마다 깨질 수 있는 것이 달라요

서비스 테스트에서 DB를 띄우면, 실패했을 때 원인이 로직인지 매핑인지 알 수 없어요. 원인을 좁히려고 다시 나눠 봐야 해서 테스트가 알려주는 정보가 줄어요.

반대로 Repository를 모킹하면 쿼리 메서드 이름 오타나 제약 위반을 **영영 못 잡아요.** 모킹한 리포지토리는 우리가 시킨 대로 답하니까요.

그래서 로직을 보는 계층은 모킹으로 좁게, 매핑과 쿼리를 보는 계층은 실제 DB로 검증해요.

### Repository는 운영과 같은 MySQL로 검증해요

H2로 검증하면 MySQL 전용 동작 — 생성 컬럼, 유니크 제약이 NULL을 다루는 방식, 정렬·문자셋 — 이 그대로 통과해 버려요. [ADR-0003](0003-schema-source-of-truth.md)에서 부분 유니크 제약을 MySQL 생성 컬럼으로 표현했기 때문에, H2로는 그 제약을 아예 검증할 수 없어요.

Testcontainers로 MySQL 8.4 LTS 이미지를 띄워요. 운영과 다른 버전으로 검증하면 검증의 의미가 줄어요.

### 검증 수단을 상황 따라 바꾸면 테스트가 거짓말을 해요

두 가지를 금지해요.

- **Docker가 없다고 H2로 바꾸지 않아요.** 바꾸는 순간 MySQL 전용 동작을 검증하려던 목적 자체가 사라지고, "통과했다"는 결과만 남아요.
- **프로덕션 버그를 테스트를 고쳐 통과시키지 않아요.** 기대값을 실제값에 맞추는 순간 그 버그는 영구히 숨겨져요. 테스트가 깨졌을 때 원인이 프로덕션인지 테스트인지 먼저 판단해요.

### 통합 테스트 클라이언트를 한 벌로 통일해요

MockMvc와 RestAssured를 나눠 쓰면 API 버전별 검증이 두 곳에서 갈라져요. `RestTestClient` 하나로 통일하기로 했어요. 선택 근거는 [기술 스택 문서](../decisions/backend-tech-stack.md)에 있어요.

## 규칙

### 계층별 전략

| 계층 | 방식 | 격리 |
| --- | --- | --- |
| 도메인 | 순수 단위 테스트 | 스프링 컨텍스트 없음 |
| Service | 단위 테스트 | Repository 모킹 |
| Controller | 단위 테스트 | Service 모킹 |
| Repository | Testcontainers(MySQL 8.4) | 실제 DB |
| 통합 | `XXXIntegrationTest` | 전체 컨텍스트 |

- 컨테이너 설정은 공통 추상 클래스로 한 번만 만들고 상속해요. 테스트 클래스마다 컨테이너를 띄우면 실행 시간이 선형으로 늘어요.
- 컨트롤러 테스트는 요청·응답 계약(상태 코드, 검증 실패 응답, 직렬화 형태)만 봐요. 비즈니스 로직 검증을 여기서 반복하지 않아요.
- `X-API-Version` 헤더로 버전을 구분하니, 버전이 지정된 엔드포인트는 헤더를 붙여 테스트하고 헤더 없는 요청의 동작도 명시적으로 검증해요.

### 작성 형식

`given / when / then` 주석 구조, 한글 메서드명, Fixture 재사용은 [코드 컨벤션](../decisions/backend-code-convention.md) 6장 규약이에요. 여기에 두 가지를 더해요.

- 메서드명은 **무엇이 보장되는지**를 문장으로 써요. `조회_테스트()`가 아니라 `없는_스튜디오를_조회하면_예외가_발생한다()`예요.
- **단언 없는 테스트는 테스트가 아니에요.** 호출만 하고 끝나는 테스트를 두지 않아요.

### Fixture

`src/test/java/com/classitda/{domain}/fixture/{Domain}Fixture.java`에 정적 메서드로 둬요.

**기본형 하나 + 변형 메서드** 구조로 만들어요. 테스트가 신경 쓰는 필드만 인자로 받고 나머지는 기본값으로 채워야, 엔티티에 필드가 추가돼도 기존 테스트가 안 깨져요.

### 케이스 선정

기능마다 최소한 다음을 덮어요.

- **정상 흐름** 1개 이상
- **경계값** — 길이·수량·시간의 최소/최대, 빈 컬렉션
- **실패 흐름** — 대상 없음, 중복, 권한 없음, 검증 실패
- **상태 전이** — 도메인에 상태가 있으면 허용/금지 전이 각각

커버리지 숫자보다 **"이 테스트가 깨지면 어떤 버그를 잡은 것인가"**에 답할 수 있는지가 기준이에요. 답할 수 없는 테스트는 지워요.

### Docker가 없는 환경

Testcontainers 테스트를 삭제하거나 H2로 바꾸지 않아요. 작성은 그대로 두고 "Docker 미가용으로 미실행"을 보고에 명시해요.

## 감수하는 점

- **Repository 테스트는 느려요.** 컨테이너를 띄워야 해서요. 공통 추상 클래스로 컨테이너를 재사용해 상쇄하지만, 단위 테스트와 같은 속도는 안 나와요.
- **로컬에 Docker가 필요해요.** 없으면 일부 테스트를 못 돌려요. 이건 [기술 스택 문서](../decisions/backend-tech-stack.md)에서 Docker를 개발 환경 전제로 둔 결정과 이어져요.
- **모킹한 서비스 테스트는 통합 지점의 오류를 못 잡아요.** 그래서 통합 테스트를 별도로 둬요. 계층별 테스트가 통합 테스트를 대신하지는 않아요.
