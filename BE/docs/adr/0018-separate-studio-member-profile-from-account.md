# ADR-0018: 시설 회원의 이름과 전화번호를 소속이 직접 가진다

## Status

Accepted (2026-08-26)

## Context

- 강사가 회원을 시설에 등록하면 전화번호로 `member` 행을 찾거나 **새로 만들어요.** 그 사람이 나중에 구글로 가입하면 인증된 번호로 그 행을 찾아 이름을 덮어쓰고 재사용해요.
- 즉 강사가 만든 껍데기 계정을 본인이 나중에 인수하는 구조예요.
- 그래서 가입한 적 없는 사람의 계정이 `member`에 쌓이고, 강사가 오타 낸 이름이 그 사람의 계정 이름이 돼요.
- 시설 회원 정보 수정 기능을 만들려는데, 지금 구조에서는 강사가 정보를 고치면 **회원 계정을 고치는 것**이 돼요. 본인 인증을 우회하고 다른 시설에도 영향이 가요.
- `studio_membership`에는 이름만 있고 전화번호가 없어요. 전화번호는 `member.phone_number` 하나뿐이에요.

## Decision

`studio_membership`이 `phone_number`를 직접 갖고, `member_id`를 nullable로 바꿔요. 강사가 회원을 등록할 때 `member` 행을 만들지 않고, 가입할 때도 `member`를 덮어쓰지 않아요.

시설이 관리하는 정보와 본인이 관리하는 계정 정보를 분리해요. 가입 시점에 인증된 번호와 같은 소속을 찾아 `member_id`를 채워 둘을 연결해요.

**가입이 끝난 소속의 전화번호는 강사가 고칠 수 없어요.** 그 번호는 SMS 인증을 거친 값이라, 임의로 바꾸면 검증이 무의미해지고 소속과 계정이 어긋나요.

## Alternatives

- **지금 구조를 두고 전화번호 수정만 막기** — 이름 오타를 고칠 방법이 없고, 껍데기 계정이 쌓이는 문제도 그대로예요.
- **가입 전 회원만 계정 정보를 수정 가능하게 하기** — "아직 가입 안 한 회원"을 API 계약에 노출해야 하고, 가입하는 순간 되던 것이 안 돼서 강사가 예측하기 어려워요.

## Consequences

- (+) 강사가 시설 회원 정보를 고쳐도 계정과 다른 시설에 영향이 없어요.
- (+) 가입하지 않은 사람의 계정이 만들어지지 않아요.
- (-) **가입한 사람과 기존 소속을 잇는 일을 애플리케이션이 직접 해야 해요.** 지금은 전화번호로 `member`를 재사용해 저절로 연결됐어요.
- (-) `member_id`가 nullable이 되면서 `(studio_id, member_id)` 유니크가 가입 전 소속에는 걸리지 않아요. 그래서 `(studio_id, phone_number)` 유니크를 함께 둬요.
- (-) `member`를 `join fetch`(inner join)로 가져오던 조회 3곳이 **`member_id`가 `NULL`인 소속을 조용히 누락해요.** `left join fetch`로 바꿔야 해요.
- (=) 이미 강사가 만들어 둔 `member` 행과 소속이 남아 있어요. `phone_number` 백필이 필요한지 확인해야 해요.
- 재검토: 소셜 제공자가 늘어 한 계정이 번호를 여러 개 갖게 되거나, 번호 없이 가입하는 경로가 생기면 연결 방식을 다시 판단해요.

## Compliance

- 강사가 회원을 등록해도 `member` 행이 늘지 않아요.
- 가입하면 같은 번호의 소속에 `member_id`가 채워져요.
- 가입이 끝난 소속의 전화번호 수정 요청은 거부돼요.
- 같은 시설에 같은 번호를 두 번 등록할 수 없어요.
