# ADR-0010. 수업 시간 충돌에 비관적 잠금을 지금 적용하지 않아요

- 상태: 채택 (2026-08-16)
- 후보: 담당 강사 소속에 쓰기 잠금, 수업 시간 범위에 읽기 잠금, 잠금 없이 애플리케이션 검증
- 선택: 현재 수업 생성에는 잠금을 적용하지 않고 애플리케이션에서 시간 겹침만 검증
- 관련: [ADR-0002](0002-integrity-enforcement-location.md)

---

## 🤔 선택 근거

### 현재 사용자 흐름에서는 부분 시간 충돌의 동시 요청 가능성이 낮아요

현재는 강사가 자신의 수업을 등록해요. 같은 강사가 서로 다른 시작 시각의 겹치는 수업을 두 기기에서 거의 동시에 등록해야 잠금 없는 검증의 빈틈이 드러나요.

등록 버튼을 중복으로 누르거나 동일한 요청을 재전송하는 경우에는 강사와 시작 시각이 같아요. 이 중복은 `uk_session_instructor_active` 유니크 키가 막아요.

### 잠금은 모든 일정 변경 경로가 같은 기준을 지켜야 의미가 있어요

담당 강사 소속을 잠금 기준으로 선택하면 같은 강사의 수업 생성을 순서대로 처리할 수 있어요. 하지만 이후 수업 수정·취소와 관리자의 담당 강사 지정도 실제 담당 강사 소속을 같은 순서로 잠가야 해요. 한 경로라도 빠지면 시간 충돌을 완전히 보장하지 못해요.

아직 없는 변경 경로까지 전제로 잠금 순서와 트랜잭션 격리 수준을 먼저 고정하면 현재 코드의 복잡성과 잠금 대기만 늘어나요. 실제 사용자 흐름이 갖춰졌을 때 함께 결정하는 편이 검증 가능해요.

## 규칙

- 수업 생성은 일반 소속 조회를 사용하고 `studio_membership`과 `class_session`에 비관적 잠금을 걸지 않아요.
- 저장 전 담당 강사의 활성 수업과 시간 구간이 겹치는지는 애플리케이션에서 확인해요.
- 수업 생성 트랜잭션의 격리 수준을 동시성 보완 목적으로 별도 변경하지 않아요.
- 일반 강사 지정이나 수업 수정·취소를 구현할 때 실제 담당 강사를 기준으로 잠금 정책을 다시 결정하고 동시성 테스트로 검증해요.

## 감수하는 점

- 시작 시각은 다르지만 시간 구간이 겹치는 두 요청이 동시에 검증되면 둘 다 저장될 수 있어요.
- 같은 강사와 같은 시작 시각의 동시 요청은 DB가 거절하지만 애플리케이션의 시간 충돌 예외가 아니라 DB 제약 예외로 응답할 수 있어요.
- 실제 운영에서 부분 시간 충돌이 관찰되면 일반 강사 지정이나 수정·취소 구현 시점 전이라도 잠금 정책을 다시 검토해요.
