# ADR-0001. BE 기능 개발을 4단계 하네스 파이프라인으로 처리해요

- 상태: 채택 (2026-08-06)
- 후보: 에이전트 한 명에게 기능을 통째로 맡기기, 설계→구현→테스트→리뷰 4단계로 나누기
- 선택: 4단계 파이프라인
- 관련: [ADR-0008](0008-review-severity.md)

---

## 🤔 선택 근거

### 생성자와 검증자가 같으면 검증이 되지 않아요

한 에이전트가 설계·구현·테스트·리뷰를 이어서 하면, 리뷰 단계에서 보는 코드가 방금 자기가 내린 판단의 결과예요. 자기 판단을 다시 승인하는 쪽으로 흐르고, 설계 단계에서 잘못 잡은 전제는 끝까지 발견되지 않아요.

단계를 나누고 각 단계를 별도 컨텍스트에서 실행하면, 뒤 단계는 앞 단계의 **산출물만** 보게 돼요. "왜 이렇게 했는지"에 대한 기억 없이 결과만 보기 때문에, 문서에 적히지 않은 암묵적 가정이 드러나요.

### 단계마다 완료 조건을 강제할 수 있어요

파이프라인으로 나누면 단계 사이에 게이트를 둘 수 있어요.

- 설계 문서에 "구현 순서"·"파일 목록"·"테스트 관점"이 비어 있으면 구현으로 넘어가지 않아요.
- 컴파일이 깨진 상태로 테스트 단계에 넘기지 않아요. 깨진 상태에서 만든 테스트·리뷰 결과는 전부 무효가 되니까요.
- 테스터가 발견한 것이 프로덕션 결함이면 테스트를 고쳐 통과시키지 않고 구현자에게 되돌려요.

### 중간 산출물이 파일로 남아야 부분 재실행이 돼요

"리뷰 지적만 반영해줘", "테스트만 보강해줘" 같은 요청이 실제로 자주 나와요. 이때 처음부터 다시 돌리면 이미 확정된 설계까지 흔들려요.

각 단계 산출물을 `BE/_workspace/`에 파일로 남기면 필요한 단계만 다시 돌릴 수 있어요. 앞 단계 결과가 입력으로 그대로 남아 있으니, 재실행해도 같은 전제 위에서 움직여요.

## 규칙

### 단계와 산출물

| 단계 | 역할 | 산출물 |
| --- | --- | --- |
| 1 설계 | 도메인 모델·API 명세·DTO 계약·예외 정책 확정 | `BE/_workspace/01_architect_design.md` |
| 2 구현 | 설계를 코드로. 테스트는 작성하지 않음 | 코드 + `02_implementer_report.md` |
| 3 테스트 | 테스트 작성·실행. 프로덕션 코드 수정 금지 | 테스트 코드 + `03_tester_report.md` |
| 4 리뷰 | 규약·설계 의도 대조, 심각도 판정 | `04_reviewer_report.md` |

요구사항 원문은 `00_input.md`에 **요약하지 말고 그대로** 남겨요. 이후 모든 판단의 근거가 이 파일이라서, 요약하는 순간 판단 기준이 한 번 굴절돼요.

### 게이트

- 설계 문서의 "열린 질문"에 **구현 방향을 바꿀 만한 가정**이 있으면 멈추고 확인해요. 필드 길이 같은 사소한 가정은 진행하고 최종 보고에 모아 알려요.
- `./gradlew compileJava`가 통과하지 않으면 테스트 단계로 넘기지 않아요.
- 테스트 실패가 프로덕션 결함이면 구현자에게 되돌려요.

### 수정 루프는 2회까지예요

결함·지적 반영 루프는 최대 2회 돌리고, 수렴하지 않으면 중단하고 남은 항목을 그대로 보고해요. 무한히 돌리는 것보다 **드러난 채로 넘기는 편**이 나아요. 2회에 안 잡히는 건 대개 사람이 판단할 문제예요.

### `BE/_workspace/`는 지우지 않아요

부분 재실행의 입력이에요. 새 기능을 시작할 때는 지우지 말고 `_workspace_{YYYYMMDD_HHMMSS}/`로 옮겨요. git에는 올리지 않아요.

### 파이프라인을 타지 않는 작업

아래는 4단계 오버헤드가 이득을 넘어요. 그냥 처리해요.

- 질문·설명 요청
- 오타·상수값 같은 한두 줄 수정
- 설계가 이미 확정된 상태의 단일 파일 편집

## 감수하는 점

- **단계 수만큼 시간과 비용이 들어요.** 그래서 위의 "파이프라인을 타지 않는 작업"을 명시적으로 뒀어요.
- **하네스 자체는 저장소로 공유되지 않아요.** `.claude/`와 `CLAUDE.md`가 `.gitignore`에 있어서, 팀원이 같은 구성을 쓰려면 각자 만들어야 해요. 그래서 지켜야 할 규칙은 하네스가 아니라 이 ADR 묶음에 남겨요 — 하네스는 개인 설정이고, ADR이 팀 합의예요.
- **단계 간 정보 손실이 있어요.** 뒤 단계는 앞 단계의 산출물만 보기 때문에, 문서에 안 적힌 맥락은 전달되지 않아요. 이건 비용이자 동시에 이 구조를 택한 이유이기도 해요.
