# ADR-0001. BE 작업을 위험에 따라 라우팅하고 기능 개발은 4단계로 처리해요

- 상태: 채택 (2026-08-06), 라우팅 규칙 개정 (2026-08-07)
- 후보: 모든 변경을 4단계로 처리, 파일 수로 예외 판정, 위험 기반 라우팅 후 기능만 4단계로 처리
- 선택: 위험 기반 4개 작업 경로 + 기능 개발의 설계→구현→테스트→리뷰 파이프라인
- 관련: [ADR-0007](0007-test-strategy.md), [ADR-0008](0008-review-severity.md)

---

## 🤔 선택 근거

### 모든 BE 작업의 위험이 같지는 않아요

질문에 답하거나 이미 있는 Docker Compose 서비스를 실행하는 일은 제품의 API·도메인·데이터 계약을 바꾸지 않아요. 이런 작업까지 기능 개발과 같은 설계 문서, 독립 테스트 단계, 독립 리뷰 단계를 거치면 검증 이득보다 시간과 컨텍스트 비용이 커져요.

반대로 한 줄 변경이어도 권한, 데이터 정합성, 상태 전이, 영속 스키마를 바꾸면 별도 설계와 검증이 필요해요. 파일 수와 코드 줄 수는 위험을 대신할 수 없어요. 그래서 작업을 크기가 아니라 **변경 효과와 실패 위험**으로 분류해요.

### 기능의 생성자와 검증자는 분리해야 해요

제품 기능은 한 에이전트가 설계·구현·테스트·리뷰를 이어서 하면 자기 판단을 다시 승인하는 쪽으로 흐를 수 있어요. 설계에서 잘못 잡은 전제도 끝까지 이어져요.

기능 개발은 단계를 별도 컨텍스트로 나누고, 뒤 단계가 앞 단계의 산출물을 기준으로 판단해요. 단계 사이에는 설계 완전성, 컴파일, 테스트, 리뷰 게이트를 둬요.

### 결정할 필요가 없는 절차는 코드와 기존 도구를 우선해요

실행 명령, 상태 확인, 설정 구문 검증처럼 절차와 성공 조건이 정해진 작업은 에이전트가 새 설계나 추상화를 만들 이유가 없어요. 기존 명령과 프로젝트 도구를 재사용하고, 요청을 만족하는 가장 작은 올바른 변경만 수행해요.

이 원칙은 보안, 데이터 정합성, 오류 처리, 접근성, 명시된 요구사항, 필수 테스트를 줄이는 근거가 아니에요.

### 모호성은 가장 비싼 경로로 해결하지 않아요

요청만으로 경로를 정할 수 없으면 먼저 읽기 전용으로 현재 상태와 영향 범위를 확인해요. 조사 전에는 파일을 수정하거나 기능 파이프라인 산출물을 만들지 않아요. 조사 결과 기능 조건이 확인될 때만 4단계 파이프라인으로 승격해요.

## 규칙

### 작업 경로

| 경로 | 대상 | 실행 방식 | 완료 검증 |
| --- | --- | --- | --- |
| `READ_ONLY` | 질문, 설명, 진단, 조회, 상태·코드 검토 | 읽기 전용 조사와 답변 | 근거 경로와 실행 결과 확인 |
| `OPERATIONAL` | 실행, 중지, 로그, 상태 확인, 기존 테스트 실행 | 기존 명령과 설정 사용, 저장소 파일 수정 금지 | 프로세스 상태, healthcheck, 연결, 명령 종료 결과 |
| `BOUNDED_CHANGE` | 설정, Docker, 빌드, CI, 개발 도구, 문서, 사소하거나 설계가 확정된 제한 변경 | 한 작업자가 조사→수정→목적별 검증→diff 점검 | 변경 목적에 직접 대응하는 가장 작은 검증 |
| `FEATURE` | 제품 계약과 위험 경계를 바꾸는 기능 개발 | 설계→구현→테스트→리뷰 | 모든 단계 게이트 통과 |

작업을 시작할 때 선택한 경로와 이유를 짧게 밝혀요. 파일 수나 코드 줄 수만으로 경로를 정하지 않아요.

### FEATURE로 분류하는 조건

다음 중 하나라도 해당하면 `FEATURE`예요.

- 공개 API의 요청·응답·오류 계약을 추가하거나 바꿔요.
- 도메인 불변식, 상태 전이, 권한 또는 인증 정책을 바꿔요.
- 영속 스키마, 데이터 마이그레이션, 데이터 정합성 또는 동시성 정책을 바꿔요.
- 여러 제품 계층을 관통하는 새 동작을 만들어요.
- 구현 전에 방향을 바꿀 수 있는 설계 대안을 선택해야 해요.
- 사용자가 전체 기능 파이프라인이나 기록된 파이프라인 재개를 명시적으로 요청해요.

로컬 실행 환경, Docker 배선, 빌드·CI 설정 자체는 제품 계약을 바꾸지 않는 한 `FEATURE`가 아니에요.

### 모호한 요청과 승격

경로가 모호하면 `READ_ONLY` 범위에서 필요한 코드, 설정, 현재 diff와 실행 상태만 확인한 뒤 분류해요. 모호하다는 이유만으로 `FEATURE`를 선택하지 않아요.

가벼운 경로로 시작한 뒤 FEATURE 조건을 발견하면 작업을 멈추고 상위 경로로 승격해요. `OPERATIONAL` 작업에서 저장소 수정이 필요해지면 `BOUNDED_CHANGE`로 승격해요. 이미 수행한 안전한 읽기와 검증은 반복하지 않아요.

### 제한 변경의 최소성

`BOUNDED_CHANGE`와 기능의 구현 단계에서는 다음 순서로 해결책을 선택해요.

1. 작업 자체가 필요한지 확인해요.
2. 저장소에 이미 있는 설정, 명령, 패턴을 재사용해요.
3. 표준 도구와 현재 설치된 의존성을 우선해요.
4. 요청되지 않은 추상화, 확장 지점, 의존성, 미래용 보일러플레이트를 만들지 않아요.
5. 요구사항을 만족하는 가장 작은 올바른 diff를 선택해요.

### 비례 검증

- `READ_ONLY`는 파일을 수정하지 않았는지와 답변 근거를 확인해요.
- `OPERATIONAL`은 실행한 명령의 종료 결과와 실제 상태를 확인해요.
- `BOUNDED_CHANGE`는 구문 검사, 대상 명령, 기동·healthcheck, 관련 컴파일이나 테스트 중 변경 목적에 필요한 검증만 실행해요.
- `FEATURE`는 [ADR-0007](0007-test-strategy.md)과 아래 4단계 게이트를 따라요.

검증 수단을 더 쉬운 대체물로 바꾸거나 실패 기대값을 실제 결함에 맞춰 약화하지 않아요.

### 기능 단계와 산출물

| 단계 | 역할 | 산출물 |
| --- | --- | --- |
| 1 설계 | 도메인 모델·API 명세·DTO 계약·예외 정책 확정 | `BE/_workspace/01_architect_design.md` |
| 2 구현 | 설계를 코드로. 테스트는 작성하지 않음 | 코드 + `02_implementer_report.md` |
| 3 테스트 | 테스트 작성·실행. 프로덕션 코드 수정 금지 | 테스트 코드 + `03_tester_report.md` |
| 4 리뷰 | 규약·설계 의도 대조, 심각도 판정 | `04_reviewer_report.md` |

요구사항 원문은 `00_input.md`에 요약하지 않고 그대로 남겨요. `_workspace/` 산출물은 `FEATURE`와 유효한 부분 재실행에만 만들어요. 다른 경로는 파이프라인에 들어갔다가 우회하지 않고 처음부터 파이프라인 밖에서 처리해요.

### 기능 게이트

- 설계 문서의 열린 질문에 구현 방향을 바꿀 만한 가정이 있으면 멈추고 확인해요. 작은 가정은 진행하되 최종 보고에 남겨요.
- `./gradlew compileJava`가 통과하지 않으면 테스트 단계로 넘기지 않아요.
- 테스트 실패가 프로덕션 결함이면 구현자에게 되돌리고 기대값을 약화하지 않아요.
- 리뷰의 P0·P1은 구현 또는 설계 단계로 되돌려요. P2만 있으면 승인할 수 있어요.

### 수정 루프는 2회까지예요

제품 결함과 P0·P1 지적의 수정 루프는 전체 기능 파이프라인에서 최대 2회 돌려요. 수렴하지 않으면 남은 항목을 숨기지 않고 미해결로 보고해요.

### `BE/_workspace/`는 기능 부분 재실행의 입력이에요

공유 규칙에서는 새 기능을 시작할 때 기존 `BE/_workspace/`를 지우지 않고 `_workspace_{YYYYMMDD_HHMMSS}/`로 옮겨요. git에는 올리지 않아요. 개인 하네스가 완료된 워크스페이스를 정리하려면 별도로 명시된 로컬 정책과 안전 검증을 따라야 해요.

## 감수하는 점

- **경로 분류에도 판단 오류가 생길 수 있어요.** 그래서 모호할 때 읽기 전용 조사부터 하고, 위험 조건을 발견하면 승격해요.
- **경량 경로에는 독립 검증자가 없어요.** 제품 계약과 위험 경계를 바꾸는 순간 FEATURE로 승격하는 것으로 범위를 제한해요.
- **기능 파이프라인은 여전히 느려요.** 높은 위험의 제품 기능에만 그 비용을 지불해요.
- **단계 간 정보 손실이 있어요.** 기능 단계는 산출물로만 맥락을 전달하므로, 설계 문서가 암묵적 가정을 빠뜨리지 않아야 해요.
