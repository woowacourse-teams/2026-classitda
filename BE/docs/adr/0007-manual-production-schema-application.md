# ADR-0007: 프로덕션 스키마를 수동으로 적용하고 마이그레이션 도구를 보류한다

## Status

Superseded by ADR-0023 (2026-08-28)

## Context

- [ADR-0002](0002-schema-source-of-truth.md)에 따라 `schema.sql`이 DDL 원본이고, JPA는 `ddl-auto: validate`로 매핑만 검증한다.
- 프로덕션 프로파일은 `spring.sql.init.mode: never`라 애플리케이션이 스키마를 만들지 않는다.
- 따라서 `schema.sql`이 바뀌면 사람이 운영 DB에 직접 반영해야 한다. RDS를 퍼블릭 액세스 없이 두었으므로 EC2를 경유한다.
- 아직 운영 데이터가 없고, 도메인 설계가 계속 바뀌어 스키마가 자주 흔들리는 단계다.
- 반영을 빠뜨리면 배포가 실패하는 것이 아니라 `validate` 단계에서 애플리케이션이 기동하지 않는다.

## Decision

Flyway 같은 마이그레이션 도구 도입을 보류하고, 당분간 `schema.sql`을 EC2를 경유해 RDS에 직접 적용한다. 스키마가 아직 크게 흔들리는 시기라 마이그레이션 스크립트를 쌓고 유지하는 비용이 지금 얻는 이득보다 크다고 판단했다.

## Alternatives

- **Flyway 도입** — 버전 관리와 재현성을 얻지만, 현재 `schema.sql`을 베이스라인으로 잘라야 하고 스키마가 흔들리는 동안 스크립트를 계속 고쳐 쓰게 된다.
- **프로덕션에서 `ddl-auto: update`** — 컬럼 삭제·타입 변경을 처리하지 못하고 ADR-0002를 정면으로 어긴다.

## Consequences

- (+) 지금 단계에서 마이그레이션 스크립트를 관리하는 부담이 없다.
- (-) 배포 절차에 사람이 하는 단계가 남는다. **이 단계를 빠뜨리면 배포는 성공했는데 앱이 기동하지 않는다.**
- (-) 누가 언제 어떤 DDL을 적용했는지 기록이 남지 않는다.
- (-) 이전 스키마로 되돌리는 절차가 없다. 애플리케이션 롤백은 자동이지만 스키마 롤백은 수동이다.
- (=) 스키마를 바꾸는 PR은 배포 담당자에게 DDL 적용 필요를 알려야 한다.
- (=) `reset-schema.sql`은 전 테이블을 DROP하므로 운영 DB에서 실행하면 안 된다.
- 재검토: 운영 데이터가 쌓여 되돌릴 수 없게 되거나, 배포 주기가 짧아져 수동 반영이 병목이 될 때. **늦어도 실제 사용자를 받기 전에 결정한다.**

## Compliance

자동 검증 수단을 두지 않는다. 스키마 변경 PR의 체크리스트에 "운영 DB에 DDL 적용" 항목을 두어 절차로 강제한다.
