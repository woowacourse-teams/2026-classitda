# ADR-0010: 데이터 계층을 관리형 서비스로 분리한다

## Status

Accepted (2026-08-19)

## Context

- 로컬 환경은 `compose.local.yml`로 애플리케이션·MySQL·Redis를 한 번에 띄운다. 프로덕션도 같은 방식이 가능하다.
- 운영 인스턴스는 `t4g.small`(2 vCPU 버스터블 / 2 GiB)이다. 애플리케이션·MySQL·Redis·Nginx를 한 대에 올리면 2 GiB를 나눠 써야 한다.
- 팀에 상시 인프라 운영 인력이 없다. 백업과 복구 절차를 직접 만들어야 한다.
- Redis에는 Refresh Session이 저장된다([ADR-0005](0005-authentication-token-and-session-boundary.md)).

## Decision

MySQL은 RDS `db.t4g.micro`, Redis는 ElastiCache(Valkey) `cache.t4g.micro`로 분리하고, EC2에는 애플리케이션과 Nginx만 둔다. 2 GiB 한 대에 전부 올리면 메모리 여유가 없고, 백업·복구 절차를 직접 만들어 유지하는 비용이 월 약 $30보다 크다고 판단했다.

## Alternatives

- **EC2 한 대에 컨테이너로 모두 구성** — 추가 비용이 없지만 메모리가 빠듯하고, 인스턴스에 문제가 생기면 데이터도 함께 위험해진다. 자동 백업이 없다.
- **ElastiCache Serverless** — 최소 과금이 월 $60을 넘어 예산 전체를 혼자 소진한다.
- **Redis만 EC2 컨테이너로, DB만 RDS** — 세션 유실은 감수할 만하지만 메모리 절약분이 크지 않아 구성을 나누는 이득이 적다.
- **ElastiCache 대신 Redis OSS 엔진** — 기능은 같으나 Valkey가 같은 사양에서 더 저렴해 Valkey를 골랐다.

## Consequences

- (+) 자동 백업, 시점 복구, 엔진 패치를 **AWS가 제공한다.** 직접 구현하지 않아도 되는 기능이다.
- (-) **다만 그 기능을 실제로 설정하지는 않았다.** 백업 보존 기간, 백업·유지 관리 윈도우, 모니터링 알람을 검토하지 않은 채 생성했다. 관리형을 고른 이유가 백업이었는데 그 값을 확인하지 않은 상태이므로, 지금은 채택 근거가 절반만 실현된 셈이다.
- (+) EC2 메모리를 애플리케이션이 대부분 쓸 수 있다.
- (-) **고정 비용이 예산의 절반을 넘는다.** 다른 리소스를 늘릴 여유가 크지 않다.
- (-) RDS를 퍼블릭 액세스 없이 두어 로컬에서 직접 접속할 수 없다. 조회·점검에 SSH 포트포워딩이 필요하다.
- (-) ElastiCache 복제본을 0으로 두었다. 노드에 장애가 생기면 Refresh Session이 전부 사라지고 사용자는 재로그인해야 한다.
- (=) 생성 시 전송 중 암호화를 켜지 않아 ElastiCache 접속이 평문이고 AUTH 토큰도 없다. `project-cache` 보안 그룹은 여러 팀이 공유하므로, 같은 VPC의 다른 인스턴스가 세션을 읽고 쓸 수 있다. **후속 과제로 남긴다.**
- (=) 팀에 리소스 삭제 권한이 없어, 구성을 바꾸려면 별도 요청이 필요하다.
- 재검토: 비용이 한도를 압박하면 Redis부터 EC2 컨테이너로 되돌린다. 세션 유실만 감수하면 되고 데이터 이전이 없다.

## Compliance

**생성 직후 확인하지 못한 항목이다. 후속으로 반드시 점검한다.**

- RDS 자동 백업이 활성화되어 있고 보존 기간이 의도한 값인지
- `FreeStorageSpace` 알람 — 스토리지 자동 조정을 껐으므로 가득 차면 DB가 멈춘다
- `BurstBalance` 알람 — 버스트 크레딧 소진 시 성능이 급락한다

배포 전 EC2에서 두 연결을 확인한다.

```
mysql -h <RDS 엔드포인트> -u <계정> -p -e "SELECT 1;"
redis-cli -h <Valkey 기본 엔드포인트> -p 6379 PING
```

ElastiCache는 기본(Primary) 엔드포인트를 사용한다. `-ro`가 붙은 리더 엔드포인트로는 세션 저장이 실패한다.
